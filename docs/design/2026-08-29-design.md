# arc — the eminix companion

Date: 2026-08-29
Status: design approved, pre-implementation
Host: rafik (ThinkPad T14 Gen 5 AMD, Ryzen 7 PRO 8840U, Radeon 780M, 14 GiB usable, no swap)
Supersedes: `~/dotfiles/docs/superpowers/specs/2026-07-18-ni-eminix-assistant-design.md`

## Goal

A local, offline, config-aware oracle that lives inside Emacs and answers
Emacs / Elisp / Linux / NixOS / org-roam questions grounded in *this machine's
actual configuration* — and whose every answer cites sources you can jump to.

The name is **arc** — an Artificial Reference Companion. Three letters and one
syllable: the shortest prefix a symbol can carry, and an arc is a sustained
spark, which is where the search for the name began.

**Namespace constraint.** `arc-mode` is a built-in Emacs library (archive
support, `arc-mode.el` in core). It defines no function of that name — the major
mode there is `archive-mode` — but the *feature* symbol is taken. arc therefore
never creates `arc-mode.el` and never calls `(provide 'arc-mode)`; the answer
buffer's major mode is **`arc-answer-mode`**, defined in `arc-ui.el`. Core
defines only two `arc-` symbols in total (`arc-mode`, `arc-insert-unibyte`), so
no other prefix collision exists.

## Problem

The current assistant (`elisa`, a fork of s-kostyaev's ELISA, wired up as
`eminix-elisa.el`) works in the sense that it answers questions. It does not
work in the sense that it is an expert on this machine. Eight concrete defects:

1. **The config corpus has almost certainly never been indexed.**
   `eminix-elisa.el` hardcodes `/home/eminix/dotfiles` and `/home/eminix/docs/org`.
   There is no `/home/eminix` on rafik; the user is `scott`. The dotfiles
   collection matches nothing and `C-c i n` points at a directory that does not
   exist. The 3.7 MB index — last written **Jul 19**, six weeks ago — is
   consistent with Info manuals and nothing else. The "config-aware" half of a
   config-aware assistant has likely never run.

   Root cause: a *distro* file hardcoded a *personal* path. eminix cannot know
   the operator's username; these values must derive from `$HOME` or be set by
   the consuming host flake.

2. **Nix builds a different package than the working tree.**
   `ioshi/i-intelligence/emacs/packages.nix` pins `fetchFromGitHub` at rev
   `61dab4e`; the checkout at `~/projects/elisa` is at `2c5207d`. The sqlite-vec
   tests are not in the running build. The prior spec also says work lands on a
   `sqlite-vec` branch; the clone is on `main`.

3. **The schema cannot express navigation.** Upstream's data model is
   `data(kind_id, collection_id, path, hash, data)` over three kinds — `web`,
   `file`, `info`. No line numbers, no titles, no node identity. Citations can
   reach a file but never a line, and there is no way to represent an org-roam
   node or a NixOS option at all.

4. **Nothing owns freshness.** Reindex is a manual command nobody remembers to
   run, and there is no indicator anywhere that the corpus has gone stale. Six
   weeks of silent rot is the predicted outcome of the design, not bad luck.

5. **The interface is upstream ellama's generic chat buffer.** No visible
   retrieved sources, no clickable citations, no way to see what was retrieved
   or why, no transient.

6. **Naming has drifted three generations.** The prior spec says `ni` /
   `scott-ni.el`; the org-roam note says `scott-elisa.el`; the actual file is
   `eminix-elisa.el`; a stale `scott-elisa.el` survives in
   `~/.config/emacs/lisp.hm-bak/`.

7. **The model list is duplicated** across `ollama.nix` (`loadModels`) and
   `eminix-elisa.el` (`eminix/elisa-models`), with a comment admitting the two
   must be hand-synced.

8. **There is no way to tell whether a change helped.** No eval set, no
   retrieval metric. Every tuning decision is a vibe.

Additionally, the corpus is missing its single most valuable source. The prior
design deferred NixOS options as "renders too large to embed" — true of the
*rendered manual*, but the structured `options.json` is 11 MB, contains 24,661
options, chunks itself, and comes straight from `cache.nixos.org` with no local
evaluation.

## Decisions

| # | Decision | Choice |
|---|---|---|
| 1 | Scope | Oracle **+ navigation**. Read-only on disk; active in Emacs. No actions, no shell, no edits. |
| 2 | Fork depth | **Hard fork.** Keep upstream's engine; extend the schema; strip what is unused. |
| 3 | Interface | **`arc-answer-mode`, derived from `org-mode`.** Citations are org links. |
| 4 | Corpus | **Five kinds**: file, info, org-node, nix-option, hm-option. |
| 5 | Freshness | **Emacs-native.** `after-save-hook` + idle sweep + `flake.lock` hash. No systemd. |
| 6 | Packaging | **Split repo + dev override.** `arc` stays its own Nix-pinned package. |
| 7 | Name | **`arc`** — Artificial Reference Companion. Free across MELPA (6,295 packages) and GNU ELPA; see the namespace constraint above for the one core collision. |

## Non-goals

- **No actions.** arc never edits a file, runs a command, or rebuilds the
  system. Navigation only. This is what keeps the surface small enough to make
  genuinely good.
- **No web search.** DuckDuckGo, searxng, webpage extraction, and pandoc are
  deleted. arc is offline by construction.
- **No complex documents.** Apache Tika and the doc/xls/pdf path are deleted.
- **No nixpkgs source indexing** in v1. Deferred, not rejected.
- **No fine-tuning.** See below.
- **No cloud fallback.**

## Evaluated and rejected

Recorded so these are not re-litigated later.

- **Cactus / Needle 2** (cactuscompute.com). Needle 2 is a 45M-parameter,
  CQ2-bit, 14 MB function-call router with a 256-token sliding window. It is not
  a knowledge model — its own README claims parity with FunctionGemma 270M and
  LFM2.5 230M, not with frontier models. (`deepseek/deepseek-v4-flash` appears
  in that repo only as the default *teacher for synthetic data generation* via
  OpenRouter.) Cactus's own quantization table shows CQ2 collapsing general
  capability: MMLU 62.33 → 33.18, GSM8K 73.67 → 0.40, HumanEval 54.88 → 1.02.
  A 256-token window cannot hold retrieved context, so it cannot be arc's
  brain. Cactus's kernels are ARM NEON, targeting phones and wearables; rafik is
  x86_64. **Deferred use:** if arc ever gains actions (explicitly a non-goal
  here), Needle is a strong candidate for the intent→structured-call layer.

- **turbovec** (Rust + Python, TurboQuant). Architecturally interesting and its
  benchmarks are credible, but adopting it means a Python sidecar process, which
  forfeits the property this whole system is built on — one process tree, inside
  Emacs, nothing to babysit. Its wins are measured at 100K–10M vectors; arc's
  corpus lands near 38K, where sqlite-vec's brute-force KNN is comfortably fast.
  **Adopted from it:** the two-stage allowlist retrieval shape (see Retrieval).

- **Fine-tuning a domain model.** Fine-tuning teaches behavior and format well
  and facts poorly. arc's domain is a configuration that changes on every
  rebuild; a fine-tune bakes in a snapshot and begins rotting immediately, while
  incremental reindex is a keystroke. If fine-tuning is revisited, the honest
  target is style and refusal discipline, not knowledge — and it should be
  measured against the eval harness below, not adopted on faith.

## Architecture

```
eminix (distro)                        dotfiles (per-host)
  eminix-arc.el                        collection paths, host overrides
    thin: prompt, keymap, defaults derived from $HOME
         |
         v
  arc  (forked package, ~/projects/arc)
    arc-db.el         schema, migrations, sqlite-vec
    arc-source-*.el   one chunker per kind
    arc-retrieve.el   scope filter -> FTS5 + vector -> fuse -> rerank
    arc-chat.el       prompt assembly, llm calls, streaming
    arc-ui.el         arc-answer-mode, citations, transient
         |
         v HTTP :11434
  Ollama (NixOS system service, Vulkan on the Radeon 780M)
```

Upstream's single 1,482-line `elisa.el` becomes six focused files. The split is
not cosmetic: the chunkers are where all new work lands and each must be
testable in isolation.

## Data model

```sql
CREATE TABLE sources (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,          -- file | info | org-node | nix-option | hm-option
  path TEXT,                   -- file: absolute path; nix-option: declarations
  org_id TEXT,                 -- org-node: roam UUID
  option_name TEXT,            -- nix-option / hm-option: services.foo.enable
  info_node TEXT,              -- info: (emacs)Directory Variables
  hash TEXT,
  mtime INTEGER,
  indexed_at INTEGER
);

CREATE TABLE data (
  id INTEGER PRIMARY KEY,
  source_id INTEGER REFERENCES sources(id) ON DELETE CASCADE,
  collection_id INTEGER REFERENCES collections(id),
  chunk TEXT,
  line_start INTEGER,
  line_end INTEGER,
  title TEXT
);

CREATE TABLE collections (id INTEGER PRIMARY KEY, name TEXT UNIQUE, enabled INTEGER);
```

Plus the sqlite-vec `vec0` embeddings table and the FTS5 mirror, as today.

**The load-bearing invariant: every chunk can render itself as an org link.**

| kind | link |
|---|---|
| file | `[[file:PATH::LINE]]` |
| info | `[[info:(emacs)Directory Variables]]` |
| org-node | `[[id:UUID][title]]` |
| nix-option | `[[nixopt:services.syncthing.enable]]` |
| hm-option | `[[hmopt:programs.git.enable]]` |

`nixopt:` and `hmopt:` are registered via `org-link-set-parameters` and open the
option's `declarations` path in nixpkgs. Because the answer buffer derives from
`org-mode`, citation navigation requires no custom code — `C-c C-o` and `RET`
already work.

## Source kinds and chunkers

- **file** — Nix and Elisp split on top-level attribute / `defun` boundaries;
  prose on paragraphs. Records true `line_start` / `line_end`. Retains upstream's
  `.gitignore` / `.ignore` / `.rgignore` handling.
- **info** — upstream's parser retained, extended to record node identity.
- **org-node** — walks via org-roam's own database rather than treating `.org`
  files as flat text. One chunk per node, carrying id, title, tags, and outline
  path. Includes the work subtree; everything stays local and offline.
- **nix-option** — reads `options.json` (11 MB, 24,661 options) from
  `cache.nixos.org` via the host flake's `system.build.manual.optionsJSON`. One
  chunk per option rendering name, type, default, example, and description;
  stores `declarations` as the navigation target.
- **hm-option** — same shape against Home-Manager's optionsJSON (~4,000 options,
  to be confirmed at implementation).

Estimated corpus: ~38,000 chunks, ~115 MB of 768-dimension float32 vectors.

## Retrieval

Two-stage, adopted from turbovec's allowlist pattern:

1. **Scope filter** produces a candidate id set — by collection, kind, org tag,
   or path prefix.
2. **FTS5 BM25 + vector KNN** run only within that set, fused by reciprocal rank
   fusion, then optionally reranked.

This replaces four near-duplicate ask commands with one function taking a scope
argument. `C-c i i` asks everything, `n` the vault, `o` options only. Adding a
scope later costs a line, not a copy-paste.

## Interface

`arc-answer-mode`, derived from `org-mode`, in the `*arc*` buffer.

```
*arc*                     corpus: fresh · 38,412 chunks

** how do I enable syncthing on this box?

   services.syncthing.enable. You already set this on rafik in
   i-service/syncthing.nix:12, with guiAddress bound to
   127.0.0.1:8385 and the UI behind auth.

*** Sources                                      [5 retrieved]
    1. [[file:~/dotfiles/ioshi/i-service/syncthing.nix::12]]
    2. [[nixopt:services.syncthing.enable]]
    3. [[id:a977180f-...][datacore backup stack]]
    4. [[info:(emacs)Directory Variables]]

   f follow-up   r retry   w capture to vault   q quit
```

- Header line carries corpus freshness per kind.
- Question is a `**` heading; answer is body; sources a `***` subtree.
- Answer streams in.
Two keymaps, deliberately distinct:

- **Global, under the retained `C-c i` prefix** — entry points that start a
  question at a given scope: `i` everything · `n` vault only · `o` options only ·
  `R` reindex · `m` model. `C-c i` with no follow-up key opens a transient, so
  none of these must be memorized.
- **In-buffer, in `arc-answer-mode`** — acting on the answer at point: `f` follow-up ·
  `r` re-retrieve · `s` change scope and re-ask · `w` capture to vault (via
  `org-capture`) · `TAB` fold · `q` quit. `org-mode`'s own bindings (`C-c C-o`,
  `RET` on a link) are inherited unchanged.

No binding outside the existing `C-c i` prefix is taken.

### Refusal contract

arc answers strictly from retrieved context and says so when it cannot. When
retrieval returns nothing above threshold, the answer is an explicit "not enough
data" naming the scope searched — never a plausible guess from parametric
memory. This is the single behaviour most worth protecting: a config oracle that
confabulates a NixOS option is worse than no oracle. It is asserted by the
prompt, and measured by negative cases in the eval set.

## Freshness

`sources.hash` and `sources.mtime` drive all incremental work.

- `after-save-hook` re-embeds a saved file already present in `sources`, async.
- org-roam's update hook re-embeds the affected node.
- A 300-second idle timer sweeps for drift with bounded work per tick.
- Options reindex when the `flake.lock` hash changes.
- The header line always shows per-kind state, so rot is visible on first glance
  rather than never.

## Testing and evaluation

- ERT tests per chunker against fixtures, one fixture set per kind.
- Schema migration tests.
- **An eval set**: ~30 questions paired with the source(s) that should be
  retrieved. `M-x arc-eval` reports recall@5. This is what converts model
  swaps and retrieval tuning from guesswork into measurement, and it is a
  prerequisite for the model upgrade below rather than an afterthought.

## Packaging

- `~/projects/elisa` is renamed to `~/projects/arc`; the GitHub fork is
  renamed to match. Every symbol takes the `arc-` prefix. Upstream's GPL-3.0
  copyright notices are retained and a statement of changes added to each
  modified file, as GPL-3 requires; the derivative remains GPL-3.0.
- `packages.nix` pins by rev as today, and gains a local-`src` dev override so
  iteration is edit-and-restart rather than commit → push → rehash → rebuild.
- The duplicated model list collapses to a single source of truth in Nix,
  exported to Emacs rather than hand-synced.
- Corpus paths derive from `$HOME`, overridable per host from the dotfiles flake.
- The system prompt is rewritten in arc's voice. The assistant introduces
  itself as arc; "elisa" survives nowhere in the shipped configuration.

## Migration

arc indexes to a new database at `~/.config/emacs/arc/arc.sqlite`. The
existing 3.7 MB `~/.config/emacs/elisa/elisa.sqlite` is not migrated — it holds
stale Info manuals and nothing else, and every kind is re-derived from source in
minutes. It is left in place until arc is confirmed working, then removed.

The stale `~/.config/emacs/lisp.hm-bak/scott-elisa.el` is deleted. The ellama
session files under `~/.config/emacs/ellama-sessions/` are **conversation
history and are left alone** — they are the operator's to keep or discard, not
this design's.

## Phasing

Each phase leaves a working assistant.

1. **Foundation** — rename, file split, new schema + migrations, `$HOME`-derived
   paths, dev override, model list de-duplication. Restores parity, correctly.
2. **Corpus** — file and info chunkers on the new schema; then org-node,
   nix-option, hm-option. The capability win.
3. **Retrieval** — scope filter, RRF fusion, reranker.
4. **Interface** — `arc-answer-mode`, org link types, citations, transient, streaming.
5. **Freshness and evaluation** — hooks, idle sweep, header line, eval harness,
   then the model upgrade measured against it.

## Open questions

1. **Reranker packaging.** Upstream's README reports the reranker improves
   retrieval quality significantly, and it is disabled by default only to reduce
   dependencies. A `nix search` for it was inconclusive; it may require a small
   derivation. Scoped as optional in v1 — the design must work without it.
2. **Home-Manager option count** (~4,000) is an estimate; confirm by building
   HM's optionsJSON at implementation time.
3. **Embedding model.** `nomic-embed-text` is carried forward unchanged for now.
   Whether `snowflake-arctic-embed2` or a newer model does better on Nix and
   Elisp text is a question for the eval harness in phase 5, not a guess now.
4. **Chat model upgrade.** `qwen2.5-coder:3b` / `qwen2.5:7b` are a generation
   behind. Replacement is deliberately deferred to phase 5 so it can be measured.
   Constraint: 14 GiB RAM, no swap — 7B at Q4 is near the practical ceiling.
