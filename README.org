* arc

[[http://www.gnu.org/licenses/gpl-3.0.txt][file:https://img.shields.io/badge/license-GPL_3-green.svg]]

arc (Artificial Reference Companion) is a local, offline, config-aware
oracle for Emacs. It answers Emacs, Elisp, Linux, NixOS and org-roam
questions grounded in this machine's actual configuration, using a
Retrieval Augmented Generation (RAG) approach, and cites the sources
you can jump to.

arc is a fork of [[http://github.com/s-kostyaev/elisa][ELISA]] by Sergey Kostyaev.

** Network access

At query time, arc makes no outbound *internet* requests. It talks to
a local [[https://ollama.com][Ollama]] instance for embeddings and chat completion, and,
only when ~arc-reranker-enabled~ is non-nil (it is nil, i.e. off, by
default), to a reranker service at ~arc-reranker-url~. Both are
loopback by default (Ollama on ~localhost:11434~, the reranker's
default ~arc-reranker-url~ is ~http://127.0.0.1:8787/~), but
~arc-reranker-url~ is a plain user-settable string -- arc will POST to
whatever it is set to, so if you point it at a non-loopback address,
that stops being a local-only request. There is no web search and no
remote document-conversion service anywhere in the package.

*Indexing* is a separate matter: building the ~nix-option~ and
~hm-option~ collections runs ~nix build~ against a flake, and that
build fetches from ~cache.nixos.org~ (and, if not already cached, a
Home-Manager revision from GitHub) over the network -- see
~arc-source-nixopt.el~. This is a one-time-per-revision cache fetch,
not an evaluation, but it is real outbound traffic, and it is the
exception to the "no internet" claim above.

** Data sources

arc indexes five kinds of source:

+ *file* :: local text files, parsed and chunked from disk.
+ *info* :: built-in and third-party Emacs info manuals.
+ *org-node* :: org-roam nodes.
+ *nix-option* :: NixOS module options.
+ *hm-option* :: Home Manager module options.

Every parse creates or updates a named collection. arc searches the
enabled collections, adds the relevant quotes to context, and lets the
LLM answer the query.

** Models

arc talks to a local [[https://ollama.com][Ollama]] instance and expects these models to be
pulled already:

+ ~qwen2.5-coder:3b~ or ~qwen2.5:7b~ for chat.
+ ~nomic-embed-text~ for embeddings.

** Installation

You need Emacs 29.2 or newer to run arc at all. Loading the ~vec0~
vector-search extension below may need more: see the note at the end
of this section.

*** Vector search extension

arc stores embeddings in sqlite using the [[https://github.com/asg017/sqlite-vec][sqlite-vec]] ~vec0~ loadable
extension. Point arc at it with the ~ARC_VEC0_PATH~ environment
variable (set this before Emacs starts, e.g. by Nix):

#+begin_src sh
export ARC_VEC0_PATH=/path/to/vec0.so
#+end_src

If ~ARC_VEC0_PATH~ is unset or does not point to an existing file, arc
does *not* warn and continue: ~arc--init-db~ checks for this explicitly
and signals a hard error, ~arc-db~ closes the half-open connection
rather than leave a broken one to be silently reused, and there is no
database at all until this is fixed. A path that exists but does not
actually provide a working ~vec0~ module (see below) fails the same
way, at the same point: ~arc--init-db~ also checks
~sqlite-load-extension~'s own return value and signals a hard error
naming the path when it is nil, rather than letting the real failure
surface much later and far from its cause when ~CREATE VIRTUAL TABLE
... USING vec0~ finally hits ~(sqlite-error "no such module: vec0")~.

Keep the file named exactly ~vec0.so~ (or your platform's
loadable-module suffix, e.g. ~vec0.dylib~) -- a copy under any other
name is liable to fail, through either of two quite different gates,
one loud and one silent. (An earlier version of this document
described only the silent one, but as SQLite's, not Emacs's, and
offered a "renamed copy loaded without incident" as proof it wasn't a
naming problem at all -- that measurement only checked whether
~sqlite-load-extension~ raised an error, and, as the next paragraph
shows, it essentially never does; the "incident" it needed to catch
happens one step later.)

The loud gate is Emacs's own: ~sqlite-load-extension~ checks the
basename you hand it against its own small, hardcoded allow-list of
extension names *before* SQLite ever sees the file, and refuses
anything not on it outright -- a copy at, say, ~/path/to/my-vec0.so~
fails immediately with =(sqlite-error "Module name not on
allowlist")=, naming its actual cause plainly. The check is
case-sensitive (~VEC0.so~ fails where ~vec0.so~ passes) and it is not
a simple substring match either: ~vec.so~ fails and ~libvec0.so~
fails even though both contain "vec0"-ish text -- only a handful of
exact recognized names pass, and this document can only report which
ones it measured, not enumerate the list from the outside.

The silent gate sits behind that one and belongs to SQLite, not
Emacs: ~sqlite-load-extension~ does not *signal* a SQLite-level load
failure, but it does *report* one -- through its own return value,
which arc's code did not check until now (see above) and which an
earlier round of this document mistook for "never fails" because it
only tested whether the call raised. Proof: copying =libz.so.1=
(zlib -- not a SQLite extension of any kind) to a file literally
named ~vec0.so~ passes the allow-list and the load call without
Emacs raising anything, but the call returns ~nil~. What determines
whether the extension you get actually behaves like ~vec0~ is
SQLite's own entry-point resolution, which arc's code cannot see or
influence: SQLite tries the generic ~sqlite3_extension_init~ symbol
first, and only if the library does not export it, falls back to a
symbol derived from the basename -- the alphabetic characters up to
the first dot, eliding a leading ~lib~ -- calling
~sqlite3_<that>_init~ if the library exports one by that name.
~vec0.so~'s binary exports no generic ~sqlite3_extension_init~, but
does export ~sqlite3_vec_init~ (and two other ~sqlite3_vec_*_init~
symbols), so *only* a basename that derives to exactly ~vec~ actually
reaches that symbol. A copy named ~rtree.so~, ~pcre.so~, or
~libsqlite3_mod_vec0.so~ passes Emacs's allow-list check by name --
~libsqlite3_mod_vec0.so~ in particular is *not* simply one more
allow-list entry copied verbatim; it passes the check for some other
reason this document cannot characterize from the outside, only
confirm by measurement -- and then "loads" in total silence:
~sqlite-load-extension~ returns ~nil~. Left unchecked, that used to
only fail once something actually tried to use the module:
=(sqlite-error "no such module: vec0")=, exactly what happened when
arc's own ~arc--init-db~ tried to create the ~data_embeddings~
virtual table. Now ~arc--init-db~ checks the ~nil~ itself and signals
immediately, naming the path (see above). Measured on Emacs 30.2; the
table below is what running both stages -- load, then ~CREATE
VIRTUAL TABLE ... USING vec0~ -- against each name actually produced:

| basename                       | ~sqlite-load-extension~ returns                 | ~USING vec0~                             |
|---------------------------------+--------------------------------------------------+-------------------------------------------|
| ~vec0.so~ / ~.dylib~ / ~.dll~   | ~t~                                              | works                                     |
| ~rtree.so~                     | ~nil~                                            | =(sqlite-error "no such module: vec0")=  |
| ~pcre.so~                      | ~nil~                                            | =(sqlite-error "no such module: vec0")=  |
| ~libsqlite3_mod_vec0.so~       | ~nil~                                            | =(sqlite-error "no such module: vec0")=  |
| zlib copied to ~vec0.so~       | ~nil~                                            | =(sqlite-error "no such module: vec0")=  |
| ~my-vec0.so~                   | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |
| ~VEC0.so~                      | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |
| ~banana.so~                    | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |
| ~libvec0.so~                   | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |
| ~vec.so~                       | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |

The upshot: renaming this file is never safe to try-and-see -- a
rename that happens to sit on Emacs's allow-list will still pass
~sqlite-load-extension~ (returning ~nil~, not raising), but arc now
catches that ~nil~ immediately, at database-open time, instead of
letting it surface later and more confusingly at first real use.

**** A possibly-higher Emacs floor for this extension specifically

This package's own code needs nothing past Emacs 29.2 (see
~Package-Requires~). Whether *loading ~vec0~* needs more is a separate
question this document cannot fully answer. It is commonly said that
~vec0~ was added to Emacs's sqlite extension allow-list some time
after Emacs 29.4 shipped, but nothing on this host -- no Emacs 29
install and no Emacs source tree -- can confirm or date that from the
outside, so treat it as unverified rather than a citable fact here.
What is confirmed directly: ~vec0~ loads and works on Emacs 30.2. If
you are on Emacs 29 and ~vec0~ loads (or doesn't) for you, we'd like
to know either way.

** Usage

*** What's built and what isn't

This is a phase 1–4-and-5-pending project. Indexing, retrieval and
answering all work end to end, ~arc-ask~ renders straight into arc's
own answer buffer, ~*arc*~, and, as of this phase, a single query can
be scoped to a subset of collections, kinds, org tags or a path prefix
-- see "Scoping a question" below. What phase 5 still has to add:
hooks that reindex a source automatically when it changes on disk, and
an automated evaluation harness -- both designed (see ~docs/design/~)
but not built. The ~*arc*~ buffer's header line reports the corpus's
size, not its freshness -- see step 6 below -- and that stays true
until phase 5's freshness tracking lands.

*** 1. Pull the Ollama models

arc expects an already-running local [[https://ollama.com][Ollama]] and these models pulled:

#+begin_src sh
ollama pull qwen2.5-coder:3b   # or: ollama pull qwen2.5:7b
ollama pull nomic-embed-text
#+end_src

~qwen2.5-coder:3b~ is ~arc-chat-provider~'s default chat model,
~nomic-embed-text~ is both providers' embedding model (see
~arc-embeddings-provider~ and ~arc-chat-provider~ in ~arc-db.el~); set
either defcustom to point at a different Ollama model instead.

*** 2. Point arc at your own files, not the author's

~arc-index-plan~ (in ~arc-index.el~) lists the collections a reindex
builds, and ~arc-collection-directory-alist~ maps the ~file~- and
~org~-chunked ones among them to a directory on disk. Both defaults
describe *this* machine, not yours:

#+begin_src elisp
;; arc-collection-directory-alist defaults to:
(("dotfiles" . "~/dotfiles")
 ("eminix"   . "~/projects/eminix")
 ("vault"    . "~/docs/org"))

;; arc-index-plan defaults to:
(("dotfiles" . file) ("eminix" . file) ("vault" . org)
 ("nix options" . nixopt) ("hm options" . hmopt)
 ("builtin manuals" . info))
#+end_src

Before indexing anything, either edit these two variables (in your
init file, with ~setopt~ or ~customize-set-variable~) to name your own
directories and collections, or remove the ~"dotfiles"~/~"eminix"~/
~"vault"~ entries entirely if you have no equivalent of them. The
~"nix options"~ and ~"hm options"~ entries also need a real flake:
see ~arc-nixopt-flake~ and ~arc-hm-flake~ (both default to
~~/dotfiles~ too) in ~arc-source-nixopt.el~ -- if you are not on
NixOS/Home-Manager, drop those two plan entries as well.

*** 3. Build the index

#+begin_src elisp
(arc-reindex-all)          ; synchronous: blocks Emacs until done
#+end_src

Do this once, from Lisp (~M-:~ or a scratch buffer), before you ever
try ~arc-ask~ -- there is nothing to retrieve until this has run at
least once. A first full index over real corpora (all of NixOS's and
Home-Manager's options, plus every configured directory) is genuinely
slow: 20–40 minutes of sustained CPU/GPU is normal, dominated by
computing one embedding per chunk. ~arc-index-nixopt-cap~ and
~arc-index-hmopt-cap~ can shrink this drastically for a quick first
try -- set either to a small number like 300 before reindexing.

Calling ~M-x arc-reindex-all~ *interactively* instead runs the
asynchronous path: it returns immediately and reports progress via
~message~, so Emacs is never frozen for the full run. Cancel an
in-progress asynchronous reindex with ~M-x arc-reindex-cancel~ --
work already committed for a source stays committed, nothing is left
half-written. Only a *synchronous* call (the Lisp form above, or
~(arc-reindex-all COLLECTIONS)~) prunes sources that have genuinely
disappeared from a collection; see "Known limitations" below.

*** 4. Enable the collections you actually want searched

~arc-enabled-collections~ -- what ~arc-ask~ actually searches --
defaults to only ~("builtin manuals")~, regardless of what
~arc-reindex-all~ just built. Add your own collections to it, e.g.:

#+begin_src elisp
(setopt arc-enabled-collections '("builtin manuals" "dotfiles" "vault"))
#+end_src

*** 5. Bind arc's commands

arc is a library and does not bind any key for you. It ships
~arc-command-map~, a prefix keymap -- bind that prefix to whatever key
you like, e.g.:

#+begin_src elisp
(keymap-set global-map "C-c i" arc-command-map)
#+end_src

| Key | Command                 | Effect                                                |
|-----+--------------------------+--------------------------------------------------------|
| ~i~ | ~arc-ask~               | Ask a question against ~arc-enabled-collections~ (or an explicit scope from Lisp). |
| ~n~ | ~arc-ask-vault~         | Ask a question scoped to ~arc-vault-collections~ (the vault only). |
| ~o~ | ~arc-ask-options~       | Ask a question scoped to ~arc-option-collections~ (NixOS and Home-Manager options only). |
| ~m~ | ~arc-toggle-chat-model~ | Cycle ~arc-chat-provider~'s model through ~arc-chat-models~. |
| ~R~ | ~arc-reindex-all~       | Reindex (synchronous from Lisp, asynchronous when called interactively -- see step 3 above). |
| ~c~ | ~arc-reindex-cancel~    | Cancel an in-progress asynchronous reindex. |

~arc-transient~ (in ~arc-ui.el~) offers the same commands as a
~transient~ menu, for whoever prefers that to a keymap.

*** 6. Ask arc something

#+begin_src
M-x arc-ask RET How do I enable syncthing in home-manager? RET
#+end_src

~arc-ask~ takes a question (a plain string; interactively it just
prompts "Ask arc: "), finds similar quotes in the enabled collections,
and streams the answer straight into arc's own buffer, ~*arc*~ --
no ellama, no separate chat package. The question becomes a heading,
the streamed answer appears under it, and a ~Sources~ subtree lists
every retrieved citation as an org link; put point on one and press
~RET~ (~arc-ui-follow-citation~) to jump to it. Call ~arc-ask~ from
Lisp with an explicit collections list to search a one-off set instead
of ~arc-enabled-collections~: ~(arc-ask "prompt" '("vault"))~.

The ~*arc*~ buffer's header line reports the corpus's size -- a chunk
count per kind, e.g. "arc · 6855 chunks · file 6427 · org-node 428" --
so you can see at a glance whether an index exists at all. It does
not report /freshness/ (whether the corpus is still up to date with
what is on disk); that tracking is phase 5.

*** Scoping a question

By default ~arc-ask~ searches ~arc-enabled-collections~, but a single
question can be scoped more narrowly along four dimensions, all
defined by ~arc-scope~ (in ~arc-scope.el~):

+ ~:collections~ -- a list of collection names, e.g. ~("vault")~.
+ ~:kinds~ -- a list of source kinds (~"file"~, ~"info"~, ~"org-node"~,
  ~"nix-option"~, ~"hm-option"~).
+ ~:tags~ -- a list of org tags. Matched the way org itself writes
  them, colon-delimited and colon-anchored, so a tag match cannot
  accidentally match a longer tag with the same ending.
+ ~:path-prefix~ -- a directory or path prefix string.

~(arc-scope :collections '("vault") :tags '("infra"))~ builds a scope
combining any of these (all given restrictions apply, ANDed together);
~(arc-scope)~, with no keys, and ~nil~ both mean the whole corpus --
*when ~arc-scope-empty-p~ or ~arc-scope-predicate~ look at them
directly.* ~arc-ask~'s second argument is a different story: a bare
~nil~ passed there is ambiguous, because it is also the historical
"caller didn't specify a scope" value, so ~arc-ask-normalize-scope~
treats it as "use ~arc-enabled-collections~", not "search everything".
For the one case where you actually want the whole corpus regardless
of ~arc-enabled-collections~, pass ~:all~ instead: ~(arc-scope :all
t)~ is a non-nil plist whose first element is a keyword, so
~arc-ask-normalize-scope~ passes it through unchanged rather than
substituting ~arc-enabled-collections~, while ~arc-scope-empty-p~
still reports it empty (it names no actual restriction), so it
retrieves against the whole corpus exactly like ~(arc-scope)~ does
when nothing rewrites it first. This is what the ~"everything"~ preset
below uses, precisely so pressing ~s~ and picking ~"everything"~ isn't
quietly narrowed to ~arc-enabled-collections~.

Pass a scope as ~arc-ask~'s second argument to search it instead of
~arc-enabled-collections~ for that one question.

The older, simpler calling convention still works unchanged:
~(arc-ask "prompt" '("vault"))~ -- a plain list of collection-name
strings -- is normalised into an equivalent ~:collections~ scope by
~arc-ask-normalize-scope~, so nothing that already calls ~arc-ask~
this way needs to change.

Two commands wrap the common cases: ~arc-ask-vault~ scopes to
~arc-vault-collections~ (the vault only, ~("vault")~ by default) and
~arc-ask-options~ scopes to ~arc-option-collections~ (~("nix options"
"hm options")~ by default) -- see the key table above (~n~ and ~o~).
Both refuse with a ~user-error~, naming the offending variable, if
that variable has been customized to ~nil~, rather than silently
widening to the whole corpus: ~(:collections nil)~ is, like plain
~nil~, an empty scope as far as ~arc-scope-empty-p~ is concerned, so
without this check a nil-ed ~arc-vault-collections~ would make
"ask the vault" search everything instead -- the opposite of what it
promises.

From inside an existing answer, ~s~ (~arc-ui-change-scope~, see "8.
In-buffer keys" below) re-asks the same question at a different scope,
picked with ~completing-read~ from ~arc-scope-presets~ (in
~arc-scope.el~) -- an alist of ~(NAME . SCOPE-PLIST)~ that defaults to
~"everything"~ (~(:all t)~, see above), ~"vault"~, ~"options"~ and
~"dotfiles"~, and that you can add your own named scopes to.

A scope that matches nothing is not a smaller answer -- it is a
refusal. When retrieval returns no candidates at all, the model is
never called; the ~*arc*~ buffer gets an explicit message instead,
naming the scope, e.g. "arc: not enough data — nothing in vault
matched this question." That is deliberate: handing an empty context
block to a chat model and hoping its prompt talks it out of answering
is exactly the failure the refusal contract exists to prevent.

*~:tags~ scoping needs a reindex.* ~sources.tags~ is populated only
when an org-node source is parsed -- from ~#+filetags~ and each
heading's own tags (see ~arc-source-org.el~) -- and only at index
time. An index built before this phase has the ~tags~ column (schema
migrations add it) but no values in it, so ~:tags~ scoping against
that index silently matches nothing, with no error, until the
collection is reindexed. Run ~(arc-reindex-all '("vault"))~ (or
whichever collection holds the org-node sources you want tag-scoped)
to populate it.

*** 7. Capture an answer to your vault

arc does not guess where your notes live -- that is exactly the kind
of assumption that let the phase 2 path bug ship a hardcoded location
and silently index nothing for six weeks. ~arc-ui-capture-function~
defaults to ~nil~, and pressing ~w~ (~arc-ui-capture~) in the ~*arc*~
buffer with it unset just reports that it is unconfigured rather than
writing anywhere. Set it to a function of one argument -- the answer
subtree at point, as a string, question heading and ~Sources~ link
list included -- to actually file answers, e.g. wired to
~org-capture~:

#+begin_src elisp
(add-to-list 'org-capture-templates
             '("a" "arc answer"
               entry (file+headline "~/docs/org/refile.org" "Captured answers")
               "%i" :immediate-finish t))

(setopt arc-ui-capture-function
        (lambda (text) (org-capture-string text "a")))
#+end_src

With point anywhere inside an answer -- its body or its ~Sources~
subtree, in a buffer that may hold several answers -- ~w~ files just
that answer, not the whole buffer.

*** 8. In-buffer keys

~arc-answer-mode~ (the major mode of ~*arc*~, derived from ~org-mode~)
binds these keys, acting on the answer or citation at point -- except
~r~, which always re-asks the most recently asked question in this
buffer, not necessarily the one at point:

| Key   | Command                    | Effect                                              |
|-------+-----------------------------+------------------------------------------------------|
| ~RET~ | ~arc-ui-follow-citation~   | Jump to the citation link at point; does nothing off a link. |
| ~TAB~ | ~org-cycle~                | Fold/unfold the answer or Sources subtree at point (plain org behaviour). |
| ~f~   | ~arc-ui-follow-up~        | Prompt for a follow-up question and ask it, at the buffer's current scope, with the answer subtree *at point* (its own question heading, body and Sources) quoted in as context, as a new answer appended to the buffer. |
| ~r~   | ~arc-ui-reask~            | Ask the most recently asked question in this buffer again, at the same scope, retrieving afresh -- useful after a bad sampling or a model swap, without retyping. |
| ~s~   | ~arc-ui-change-scope~     | Re-ask the most recently asked question in this buffer at a different scope, picked from ~arc-scope-presets~ (see "Scoping a question" above). |
| ~w~   | ~arc-ui-capture~          | File the answer at point via ~arc-ui-capture-function~ (see above); reports that it is unconfigured rather than writing anywhere if that is unset. |
| ~q~   | ~arc-ui-quit~             | Bury the ~*arc*~ buffer. |

~r~ reads ~arc-ui--last-question~ -- the most recently *asked* question
in this buffer -- and re-asks exactly that, regardless of where point
is; that is the right source for "ask the last question again". ~f~
is deliberately different: a multi-answer buffer invites scrolling
back to an earlier answer before following up on it, so ~f~ builds its
prompt entirely from the answer subtree at point via
~arc-ui-answer-at-point~ -- which already opens with its own
~** question~ heading -- rather than naming the question separately
from ~arc-ui--last-question~, which would risk pairing one answer's
text with a different (and possibly much later) question. ~s~ is
deliberately re-asking the same question at a new scope for the same
reason ~r~ does: it reads ~arc-ui--last-question~, not the answer at
point.

~r~ and ~f~ both also read ~arc-ui--last-scope~ -- the scope the
buffer's most recent answer was actually retrieved at -- and pass it
straight back to ~arc-ask~, so re-asking or following up stays at
whatever scope ~s~ (or the entry point that started the buffer, ~i~,
~n~ or ~o~) last put the buffer at. Passing ~nil~ there instead would
not mean "the same scope again" -- as with ~arc-ask~ generally (see
"Scoping a question" above), ~nil~ means "fall back to
~arc-enabled-collections~" -- so without this, asking with ~n~ (the
vault) and then pressing ~r~ would silently re-ask against
~arc-enabled-collections~ instead of staying in the vault.

All three -- ~f~, ~r~ and ~s~ -- guard on
~arc-ui--last-question~ being non-nil before doing anything, and
signal a ~user-error~ in a buffer that has never had ~arc-ask~ render
an answer into it.

*** Retrieval strategy and its knobs

Retrieval picks between two vector-search strategies per query, and
which one it picks depends on the scope's size, not the corpus's:

+ *KNN* -- ask the ~vec0~ extension's nearest-neighbour operator for
  the ~k~ nearest rows, globally, then keep the ones inside the scope.
  Fast, but the operator's ~k~ result rows are chosen before scoping
  is applied, so a narrow scope needs ~k~ raised well past
  ~arc-knn-candidates~ to have a chance of returning enough in-scope
  rows -- and sqlite-vec 0.1.6 refuses any ~k~ over *4096* (measured:
  ~k = 7405~, the full corpus size, errors with "k value in knn query
  too large").
+ *Brute force* -- compute ~vec_distance_cosine~ directly against
  every row the scope admits, with no ~k~ at all. Exact, and its cost
  tracks the scope's size, not the corpus's, because SQLite only
  evaluates the distance function on the rows the join admits: measured
  at roughly 0.2 ms per row in scope, 54 ms for a 428-row scope and
  1.59 s across the full 7,405-row corpus.

Two ~defcustom~s tune the choice, both in ~arc-scope.el~:

+ ~arc-knn-candidates~ (default 40) -- how many nearest neighbours
  retrieval wants, in or out of scope. For an unscoped query this is
  ~k~ directly; for a scoped one it is what ~arc-scope-vector-plan~
  scales ~k~ up to approximate, or the number of rows brute force pulls
  in scope order.
+ ~arc-scope-bruteforce-max~ (default 2000) -- the largest scope, in
  chunks, searched by brute force rather than a scaled-up KNN. Above
  it, ~arc-scope-vector-plan~ scales ~k~ by the ratio of corpus size to
  scope size; if that scaled ~k~ would exceed the 4096 ceiling, brute
  force runs regardless of cost, because there is no ~k~ that could
  work instead.

2000 was picked to keep brute force's worst case near 400 ms at
roughly 0.2 ms/row -- both defaults are plain numbers, not magic
constants, and are fair to argue with once your own corpus's size and
your own patience for a slow query are on the table.

Both actually take effect where the decision is made. ~arc-find-similar~
(what these two tune) runs inside a forked, ~emacs -Q~-equivalent child
process (~async-start~, via ~arc--async-do~), which never loads your
init file, so any ~defcustom~ read there sees only its compiled-in
default unless the parent explicitly captures the live value and hands
it across with ~async-inject-variables~. ~arc-knn-candidates~ and
~arc-scope-bruteforce-max~ are on that injection list, along with
~arc-limit~ and ~arc-reranker-limit~ (read via ~arc-get-limit~, which
picks the answer context size) and ~arc-embedding-size~ (read when the
child opens its own database connection, which it always does, having
no cached one to inherit) -- so customizing any of these in your init
file does change retrieval in the real, asynchronous path, not just in
a synchronous call from ~M-:~. ~test/test-arc-async-injection.el~
guards this by walking the actual call graph the child runs and
failing if some future callee reads a new tunable that isn't on the
injection list.

** Known limitations

*** Asynchronous reindex never removes departed sources

~M-x arc-reindex-all~ (the interactive, non-blocking path -- see its
docstring) does not prune. A source that has genuinely left the corpus
(deleted, gitignored, newly excluded) keeps whatever content it was
last indexed with and stays citable indefinitely under this path
alone. This is deliberate, not an oversight: a long-running
asynchronous walk only ever knows "what this run has reached so far",
never "everything this collection currently has", and three separate
attempts to prune from the former each turned into a real, reproduced
way to delete sources the run had simply not gotten to yet.

Only a *synchronous* reindex prunes -- run one occasionally to actually
remove departed sources:

#+begin_src elisp
(arc-reindex-all)                  ; every collection in `arc-index-plan'
(arc-reindex-all '("dotfiles"))     ; just one collection
#+end_src

*** Emptying a collection's only source leaves it indexed

The synchronous prune above refuses to prune anything when a
collection's walk comes back with zero sources, on purpose -- see
~arc--prune-collection~'s docstring -- because an empty result is
indistinguishable from a directory that is merely momentarily empty
(unmounted, a sync tool mid-catch-up), and deleting a whole collection
is never the right answer to that ambiguity. One consequence: if a
collection has exactly one source and that source is edited down to
zero chunks (an emptied or now-whitespace-only file, say), the walk
that reindexes it also comes back with zero kept ids, the same refusal
applies, and that now-empty source's *old* content stays indexed and
citable indefinitely -- reindexing never removes it, because from
here a genuinely-emptied sole source and a not-yet-ready directory
look identical. Adding an unrelated second source to the same
collection is enough to make the emptied one prunable again on the
next synchronous reindex, since the walk then yields a non-empty
kept-ids list to check it against.
