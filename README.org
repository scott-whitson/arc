* arc

[[http://www.gnu.org/licenses/gpl-3.0.txt][file:https://img.shields.io/badge/license-GPL_3-green.svg]]

arc (Artificial Reference Companion) is a local, offline, config-aware
retrieval engine for Emacs. It indexes this machine's files, manuals,
org-roam notes, and NixOS/Home-Manager options; searches them with a
hybrid of keyword and vector retrieval; and returns ranked source records
with citations you can jump to. arc does not generate prose: an external
agent or caller owns any language-model response.

arc is a fork of [[http://github.com/s-kostyaev/elisa][ELISA]] by Sergey Kostyaev.

** Network access

With the default configuration, query-time retrieval makes no outbound
*internet* requests: embeddings use a local [[https://ollama.com][Ollama]] instance
and ~arc-reranker-enabled~ is nil, so no reranker request is made. A custom
~arc-embeddings-provider~ may be remote, and enabling the reranker can POST to
whatever ~arc-reranker-url~ names; both are loopback by default (Ollama on
~localhost:11434~, the reranker's default ~arc-reranker-url~ is
~http://127.0.0.1:8787/~), but a non-loopback setting is not local-only. The
keyword arm (for example, ~bin/arc search ... --arm keyword~) skips embedding
calls entirely. There is no web search or remote document-conversion service
built into the package.

*Indexing* is a separate matter: building the ~nix-option~ and
~hm-option~ collections runs ~nix build~ against a flake, and that
build fetches from ~cache.nixos.org~ (and, if not already cached, a
Home-Manager revision from GitHub) over the network -- see
~arc-source-nixopt.el~. This is a one-time-per-revision cache fetch,
not an evaluation, but it is real outbound traffic, and it is the
exception to the "no internet" claim above.

** Data sources

arc indexes five kinds of source:

+ *file* :: local text files, parsed and chunked from disk.
+ *info* :: built-in and third-party Emacs info manuals.
+ *org-node* :: org-roam nodes.
+ *nix-option* :: NixOS module options.
+ *hm-option* :: Home Manager module options.

Every parse creates or updates a named collection. arc searches the enabled
collections and returns the relevant documents, passages, scores, and
navigable source links to the caller.

** Search

arc exposes the index through an interactive document search surface and
through a JSON tool interface; neither path generates prose.

+ ~M-x arc-search~ :: minibuffer search. Types on the BM25 arm, which needs no
  embedding call and returns in tens of milliseconds, then -- once you pause --
  the same invocation re-ranks the whole list with the full hybrid's own
  ordering, not just what BM25 missed. There is no arc-side delay to tune:
  timing is consult's own, governed by ~consult-async-input-debounce~, which
  restarts the computation if a keystroke interrupts it. The marginalia
  annotation on each candidate says which arm actually produced it, so you can
  see the keyword-only paint settle into the fused one. Requires ~consult~;
  arc loads and works without it, minus this command.
+ ~M-x arc-search-show~ :: the same search rendered into ~*arc-search*~, where
  ~TAB~ expands a document to every passage that matched, ~g~ re-runs and ~s~
  re-scopes.

Results are *documents*, not chunks. arc's corpus mixes one-chunk sources (nix
options, Info nodes) with sources that split into dozens (vault notes, long
configuration files, agent transcripts), so a chunk-level result list lets one
long note fill every slot.
~arc-rollup-function~ chooses how a document's score is aggregated from its
chunks'; see ~docs/design/2026-09-13-rollup-measurement.md~ for the sweep that
picked the default.

*** As a tool

~bin/arc~ exposes ~search~, ~scopes~, ~stats~, ~preview~, ~lifecycle~, and
~mcp~ to anything outside Emacs, through ~emacsclient~ and the running daemon
-- so the database stays warm and there is no second index process to babysit.
Symlink it onto ~PATH~:

#+begin_src sh
ln -s /path/to/arc/bin/arc ~/.local/bin/arc
arc search "disk layout" --scope home --kind file --json
arc preview 42 --json
arc lifecycle --json
#+end_src

~search~ returns ranked documents and matching passages. ~preview~ retrieves
bounded passages plus source metadata for a stable ~source_id~ returned by
search. ~scopes~ enumerates named presets; ~stats~ reports corpus counts,
provenance, indexing times, and freshness; ~lifecycle~ is a read-only report
of missing, stale, phantom, and orphaned records. The typed search filters
(~--collection~, ~--kind~, ~--tag~, and ~--path-prefix~) are compiled into an
intersection, not a free-form query language; an ambiguous preset/filter
combination is rejected rather than broadened silently. ~--path-prefix~ takes
an *absolute* path, because stored paths are absolute: a relative prefix is
refused rather than answered with an empty result set that reads as "no such
document".

~mcp~ starts a local stdio MCP server. It exposes the same five read-only
operations -- search, preview, scopes, stats, and lifecycle -- to an MCP
client as a local subprocess. The subprocess itself has no URL or cloud
dependency, but a search using a custom remote embedding provider or an
enabled remote reranker follows that provider's network behavior; the
keyword arm skips embedding calls. See [[file:docs/mcp.md][docs/mcp.md]] for
the configuration example and the retrieved-data trust boundary.

Exit status is 0 on success, 1 on error, and 2 specifically when the Emacs
daemon is not running -- the one failure mode this transport has that the
in-Emacs commands do not.

There is deliberately no ~ask~ verb. A caller that wants prose already has its
own model; arc's job here is retrieval.

** Models

The retrieval engine does not require a chat model. The default embedding
provider is local [[https://ollama.com][Ollama]] with ~nomic-embed-text~; callers may
configure another, potentially remote, embedding provider. The optional
reranker is a separate service and is disabled by default. Keyword-only
retrieval skips embedding calls.

** Installation

You need Emacs 29.2 or newer to run arc at all. Loading the ~vec0~
vector-search extension below may need more: see the note at the end
of this section.

*** Vector search extension

arc stores embeddings in sqlite using the [[https://github.com/asg017/sqlite-vec][sqlite-vec]] ~vec0~ loadable
extension. Point arc at it with the ~ARC_VEC0_PATH~ environment
variable (set this before Emacs starts, e.g. by Nix):

#+begin_src sh
export ARC_VEC0_PATH=/path/to/vec0.so
#+end_src

If ~ARC_VEC0_PATH~ is unset or does not point to an existing file, arc
does *not* warn and continue: ~arc--init-db~ checks for this explicitly
and signals a hard error, ~arc-db~ closes the half-open connection
rather than leave a broken one to be silently reused, and there is no
database at all until this is fixed. A path that exists but does not
actually provide a working ~vec0~ module (see below) fails the same
way, at the same point: ~arc--init-db~ also checks
~sqlite-load-extension~'s own return value and signals a hard error
naming the path when it is nil, rather than letting the real failure
surface much later and far from its cause when ~CREATE VIRTUAL TABLE
... USING vec0~ finally hits ~(sqlite-error "no such module: vec0")~.

Keep the file named exactly ~vec0.so~ (or your platform's
loadable-module suffix, e.g. ~vec0.dylib~) -- a copy under any other
name is liable to fail, through either of two quite different gates,
one loud and one silent. (An earlier version of this document
described only the silent one, but as SQLite's, not Emacs's, and
offered a "renamed copy loaded without incident" as proof it wasn't a
naming problem at all -- that measurement only checked whether
~sqlite-load-extension~ raised an error, and, as the next paragraph
shows, it essentially never does; the "incident" it needed to catch
happens one step later.)

The loud gate is Emacs's own: ~sqlite-load-extension~ checks the
basename you hand it against its own small, hardcoded allow-list of
extension names *before* SQLite ever sees the file, and refuses
anything not on it outright -- a copy at, say, ~/path/to/my-vec0.so~
fails immediately with =(sqlite-error "Module name not on
allowlist")=, naming its actual cause plainly. The check is
case-sensitive (~VEC0.so~ fails where ~vec0.so~ passes) and it is not
a simple substring match either: ~vec.so~ fails and ~libvec0.so~
fails even though both contain "vec0"-ish text -- only a handful of
exact recognized names pass, and this document can only report which
ones it measured, not enumerate the list from the outside.

The silent gate sits behind that one and belongs to SQLite, not
Emacs: ~sqlite-load-extension~ does not *signal* a SQLite-level load
failure, but it does *report* one -- through its own return value,
which arc's code did not check until now (see above) and which an
earlier round of this document mistook for "never fails" because it
only tested whether the call raised. Proof: copying =libz.so.1=
(zlib -- not a SQLite extension of any kind) to a file literally
named ~vec0.so~ passes the allow-list and the load call without
Emacs raising anything, but the call returns ~nil~. What determines
whether the extension you get actually behaves like ~vec0~ is
SQLite's own entry-point resolution, which arc's code cannot see or
influence: SQLite tries the generic ~sqlite3_extension_init~ symbol
first, and only if the library does not export it, falls back to a
symbol derived from the basename -- the alphabetic characters up to
the first dot, eliding a leading ~lib~ -- calling
~sqlite3_<that>_init~ if the library exports one by that name.
~vec0.so~'s binary exports no generic ~sqlite3_extension_init~, but
does export ~sqlite3_vec_init~ (and two other ~sqlite3_vec_*_init~
symbols), so *only* a basename that derives to exactly ~vec~ actually
reaches that symbol. A copy named ~rtree.so~, ~pcre.so~, or
~libsqlite3_mod_vec0.so~ passes Emacs's allow-list check by name --
~libsqlite3_mod_vec0.so~ in particular is *not* simply one more
allow-list entry copied verbatim; it passes the check for some other
reason this document cannot characterize from the outside, only
confirm by measurement -- and then "loads" in total silence:
~sqlite-load-extension~ returns ~nil~. Left unchecked, that used to
only fail once something actually tried to use the module:
=(sqlite-error "no such module: vec0")=, exactly what happened when
arc's own ~arc--init-db~ tried to create the ~data_embeddings~
virtual table. Now ~arc--init-db~ checks the ~nil~ itself and signals
immediately, naming the path (see above). Measured on Emacs 30.2; the
table below is what running both stages -- load, then ~CREATE
VIRTUAL TABLE ... USING vec0~ -- against each name actually produced:

| basename                       | ~sqlite-load-extension~ returns                 | ~USING vec0~                             |
|---------------------------------+--------------------------------------------------+-------------------------------------------|
| ~vec0.so~ / ~.dylib~ / ~.dll~   | ~t~                                              | works                                     |
| ~rtree.so~                     | ~nil~                                            | =(sqlite-error "no such module: vec0")=  |
| ~pcre.so~                      | ~nil~                                            | =(sqlite-error "no such module: vec0")=  |
| ~libsqlite3_mod_vec0.so~       | ~nil~                                            | =(sqlite-error "no such module: vec0")=  |
| zlib copied to ~vec0.so~       | ~nil~                                            | =(sqlite-error "no such module: vec0")=  |
| ~my-vec0.so~                   | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |
| ~VEC0.so~                      | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |
| ~banana.so~                    | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |
| ~libvec0.so~                   | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |
| ~vec.so~                       | =(sqlite-error "Module name not on allowlist")=  | n/a                                       |

The upshot: renaming this file is never safe to try-and-see -- a
rename that happens to sit on Emacs's allow-list will still pass
~sqlite-load-extension~ (returning ~nil~, not raising), but arc now
catches that ~nil~ immediately, at database-open time, instead of
letting it surface later and more confusingly at first real use.

**** A possibly-higher Emacs floor for this extension specifically

This package's own code needs nothing past Emacs 29.2 (see
~Package-Requires~). Whether *loading ~vec0~* needs more is a separate
question this document cannot fully answer. It is commonly said that
~vec0~ was added to Emacs's sqlite extension allow-list some time
after Emacs 29.4 shipped, but nothing on this host -- no Emacs 29
install and no Emacs source tree -- can confirm or date that from the
outside, so treat it as unverified rather than a citable fact here.
What is confirmed directly: ~vec0~ loads and works on Emacs 30.2. If
you are on Emacs 29 and ~vec0~ loads (or doesn't) for you, we'd like
to know either way.

** Usage

*** What's built and what isn't

Indexing, retrieval, freshness tracking, evaluation, document search, and
the agent-facing tool surface are implemented. A query can be scoped to a
subset of collections, kinds, org tags, or a path prefix. ARC returns
retrieval results; a caller that needs prose supplies its own model. The
prose/chat layer was deliberately removed so the package has one clear
responsibility: make local evidence easy to retrieve, inspect, and navigate.

*** 1. Prepare the embedding provider

The default embedding provider is local [[https://ollama.com][Ollama]]. Pull the embedding
model before indexing:

#+begin_src sh
ollama pull nomic-embed-text
#+end_src

Set ~arc-embeddings-provider~ if the machine uses another provider. No
chat model is installed or contacted by ARC.

*** 2. Point arc at your own files, not the author's

~arc-index-plan~ (in ~arc-index.el~) lists the collections a reindex
builds, and ~arc-collection-directory-alist~ maps the ~file~- and
~org~-chunked ones among them to a directory on disk. Both defaults
describe *this* machine, not yours:

#+begin_src elisp
;; arc-collection-directory-alist defaults to:
(("vault"       . "~/docs/org")
 ("home"        . "~")
 ("emacs"       . "~/.config/emacs")
 ("claude"      . "~/.claude")
 ("agent-shell" . "~/.agent-shell")
 ("mail"        . "~/.mail"))

;; arc-index-plan defaults to (note: no "mail"):
(("vault" . org) ("home" . file) ("emacs" . file)
 ("claude" . file) ("agent-shell" . file)
 ("nix options" . nixopt) ("hm options" . hmopt)
 ("builtin manuals" . info))
#+end_src

Before indexing anything, either edit these two variables (in your
init file, with ~setopt~ or ~customize-set-variable~) to name your own
directories and collections, or remove the entries you have no
equivalent of. ~"mail"~ is configured but deliberately absent from
~arc-index-plan~: add it there to index mail, and nothing will do so
until you do. The ~"nix options"~ and ~"hm options"~ entries also need
a real flake: see ~arc-nixopt-flake~ and ~arc-hm-flake~ (both default
to ~~/dotfiles~ too) in ~arc-source-nixopt.el~ -- if you are not on
NixOS/Home-Manager, drop those two plan entries as well.

*** 2b. Exclude what the =home= collection overlaps

The =home= collection is rooted at =$HOME=, so two exclusions have to live
outside this repo, in files you write once:

=~/.arcignore=:
#+begin_example
docs/org/
downloads/
#+end_example

=docs/org/= is owned by =vault=, which indexes it with the org chunker; without
this line every note is indexed twice, and the second copy has no org id.
=downloads/= is installer and ISO junk.

=~/.config/emacs/.arcignore=:
#+begin_example
elpa/
eln-cache/
auto-save-list/
ellama-sessions/
arc/
#+end_example

=arc/= is where =arc-db-directory= puts =arc.sqlite=. Indexing it is also
blocked by =arc-secret-denylist=, which covers the case where you have pointed
=arc-db-directory= somewhere else; the line here is the belt to that pair of
braces.

Nothing else needs excluding: =arc-ignore-invisible-files= is =t=, so every
other dotted directory under =$HOME= -- =~/.cache=, =~/.local=, =~/.pi=,
browser and password-manager caches -- is already out of =home=.

If you skip this step, ~arc-reindex-all~ says so before it starts: it warns,
once per run, for every planned collection whose directory sits inside another
planned collection's with nothing excluding the overlap, naming both and the
line to add. It is a warning and not a refusal -- the overlap is a
misconfiguration, not a corruption -- but an unheeded one costs you a doubled
=vault=, chunked the second time with no org id, no title and no citable link.

*** 3. Build the index

#+begin_src elisp
(arc-reindex-all)          ; synchronous: blocks Emacs until done
#+end_src

Do this once, from Lisp (~M-:~ or a scratch buffer), before searching --
there is nothing to retrieve until the index has been built. A first full
index over real corpora (all of NixOS's and Home-Manager's options, plus
every configured directory) is genuinely slow: 20–40 minutes of sustained
CPU/GPU is normal, dominated by computing one embedding per chunk.
~arc-index-nixopt-cap~ and ~arc-index-hmopt-cap~ can shrink this drastically
for a quick first try -- set either to a small number like 300 before
reindexing.

Calling ~M-x arc-reindex-all~ *interactively* instead runs the
asynchronous path: it returns immediately and reports progress via
~message~, so Emacs is never frozen for the full run. Cancel an
in-progress asynchronous reindex with ~M-x arc-reindex-cancel~ --
work already committed for a source stays committed, nothing is left
half-written. Only a *synchronous* call (the Lisp form above, or
~(arc-reindex-all COLLECTIONS)~) prunes sources that have genuinely
disappeared from a collection; see "Known limitations" below.

*** 4. Enable the collections you actually want searched

~arc-enabled-collections~ -- the collections used when a caller supplies
no scope -- defaults to only ~("builtin manuals")~, regardless of what
~arc-reindex-all~ just built. Add your own collections to it, e.g.:

#+begin_src elisp
(setopt arc-enabled-collections '("builtin manuals" "home" "vault"))
#+end_src

*** 5. Bind arc's commands

arc is a library and does not bind any key for you. Bind the retrieval
entry points according to the surrounding Emacs configuration, e.g.:

#+begin_src elisp
(global-set-key (kbd "C-c i s") #'arc-search-show)
(global-set-key (kbd "C-c i R") #'arc-reindex-all)
(global-set-key (kbd "C-c i c") #'arc-reindex-cancel)
#+end_src

| Command | Effect |
|---------+--------|
| ~arc-search-show~ | Prompt for a query and render ranked documents in ~*arc-search*~. |
| ~arc-search~ | Optional Consult minibuffer search; keyword results settle into hybrid ranking. |
| ~arc-reindex-all~ | Rebuild one or more collections (asynchronous when called interactively). |
| ~arc-reindex-cancel~ | Cancel an in-progress asynchronous reindex. |
| ~arc-freshness~ | Show which collections have drifted from their indexed inputs. |

The search buffer uses ~TAB~ to expand passages, ~g~ to rerun, ~s~ to change
scope, and ~RET~ to visit the best-matching source location.

*** 6. Search the corpus

#+begin_src
M-x arc-search-show RET disk layout RET
#+end_src

~arc-search-show~ renders one line per matching document in ~*arc-search*~,
with the best-matching passages beneath it. The result buffer carries the
source identity and passage metadata needed to visit a file, Info node,
org-roam node, NixOS option, or Home-Manager option. It never asks a chat
model to rewrite the result. For a fast interactive front door, use
~arc-search~ when Consult is installed; it paints the keyword arm first and
then replaces it with the fused ranking.

*** Scoping a search

By default a search uses ~arc-enabled-collections~, but a query can be
scoped more narrowly along four dimensions, all defined by ~arc-scope~ in
~arc-scope.el~. The same dimensions are available to ~bin/arc search~ as
validated typed flags and to the MCP ~arc_search~ tool:

+ ~:collections~ -- a list of collection names, e.g. ~("vault")~.
+ ~:kinds~ -- a list of source kinds (~"file"~, ~"info"~, ~"org-node"~,
  ~"nix-option"~, ~"hm-option"~).
+ ~:tags~ -- a list of org tags, matched colon-delimited and colon-anchored.
+ ~:path-prefix~ -- an absolute directory or path prefix string. Sources
  store absolute paths, so a relative prefix matches nothing. ~bin/arc~
  refuses a relative ~--path-prefix~ for that reason.

~(arc-scope :collections '("vault") :tags '("infra"))~ combines restrictions
with AND. ~arc-scope-normalize~ accepts nil (use the enabled collections),
a plain collection-name list, or a scope plist. Use ~(:all t)~ when an
explicit whole-corpus scope is required. A scope that matches nothing
returns no documents; callers can use that empty result as a refusal rather
than turning an empty context into a guessed answer.

*~:tags~ scoping needs a reindex.* ~sources.tags~ is populated when an
org-node source is parsed. Reindex the relevant collection before relying on
tag filtering.

*** Deterministic priority rules

~arc-search-priority-rules~ is an optional, explicit list of query/source
boosts. It is nil by default and never learns from clicks, opened results, or
browsing history. A rule matches a query regexp plus one source identity
constraint (path prefix, kind, option name, org ID, or Info node), then adds a
fixed numeric boost before the document limit is applied. Ties remain
stable. Keep the rules disabled when running retrieval evaluation so the
baseline stays measurable.

For example, a consuming configuration can prefer the local Emanix source for
syncthing questions without changing the underlying retrieval scores:

#+begin_src elisp
(setopt arc-search-priority-rules
        '((:query "syncthing"
           :path-prefix "/srv/notes/ioshi/i-intelligence/"
           :boost 1000)))
#+end_src

An absolute prefix, like every other path prefix: sources store absolute
paths, so a relative one matches nothing.

The rule is a display preference, not an authority claim: source provenance,
freshness, and the retrieved-data trust boundary still apply.

*** 7. Search as a tool

The retrieval engine is also callable by an external agent through the warm
Emacs daemon:

#+begin_src sh
arc search "disk layout" --scope home --kind file --json
arc preview 42 --json
arc scopes --json
arc stats --json
arc lifecycle --json
#+end_src

~bin/arc search~ returns ranked documents, matching passages, a stable
~source_id~, source identity, and an explicit retrieved-data trust marker.
Every result also carries the source's ~tags~ as an array -- empty rather than
null when a source has none -- so a caller that filtered by tag can see which
of its hits actually carried that tag instead of inferring it from the filter
it sent.
~preview~ follows that identifier to bounded source metadata and passages;
callers should search first and preview only the sources they need. ~scopes~
enumerates the names instead of making a caller guess. ~stats~ reports corpus
counts, provenance, per-collection indexing times, and freshness states.
~lifecycle~ is read-only: it reports drift and structural leftovers but never
deletes or reindexes anything. Exit status 2 means the Emacs daemon is not
running; status 1 is an ordinary command error.

The JSON surface is deliberately retrieval-only. An external agent is already
the component that can synthesize prose, while ARC supplies local evidence and
source identity. Retrieved text is data, not instructions: a caller must not
execute commands, broaden scope, disclose secrets, or invoke another tool
because a passage tells it to.

*** 8. Freshness and evaluation

~M-x arc-freshness~ reports which collections have drifted from their indexed
inputs. ~arc-watch-mode~ reindexes changed file and org-node sources after a
save and during bounded idle sweeps. Derived option and manual collections are
reported stale rather than rebuilt automatically: a full re-embedding run is
too expensive to start silently.

~M-x arc-eval~ runs the private retrieval question set and reports recall at
the configured cutoffs. It never calls a chat model. The harness can compare
the fused, semantic, and keyword arms, and can measure document-level recall
and rollup strategies. Use this measurement before changing an embedding
provider, retrieval limit, or rollup function.

The prose-generation layer and chat-model reranker have been removed. ARC now
has one responsibility: index, search, measure, and expose citable local
evidence. Applications that need prose should call the search/tool surfaces
and provide their own writer.

The old prose commands ~arc-ask~, ~arc-ask-vault~, ~arc-ask-options~, and

or ~bin/arc search~ for retrieval; the caller owns any prose response. The
former ~arc-ask-normalize-scope~ name remains as an obsolete compatibility alias
for ~arc-scope-normalize~ so existing callers can migrate without a silent

*** Retrieval strategy and its knobs

Retrieval picks between two vector-search strategies per query, and
which one it picks depends on the scope's size, not the corpus's:

+ *KNN* -- ask the ~vec0~ extension's nearest-neighbour operator for
  the ~k~ nearest rows, globally, then keep the ones inside the scope.
  Fast, but the operator's ~k~ result rows are chosen before scoping
  is applied, so a narrow scope needs ~k~ raised well past
  ~arc-knn-candidates~ to have a chance of returning enough in-scope
  rows -- and sqlite-vec 0.1.6 refuses any ~k~ over *4096* (measured:
  ~k = 7405~, the full corpus size, errors with "k value in knn query
  too large").
+ *Brute force* -- compute ~vec_distance_cosine~ directly against
  every row the scope admits, with no ~k~ at all. Exact, and its cost
  tracks the scope's size, not the corpus's, because SQLite only
  evaluates the distance function on the rows the join admits: measured
  at roughly 0.2 ms per row in scope, 54 ms for a 428-row scope and
  1.59 s across the full 7,405-row corpus.

Two ~defcustom~s tune the choice, both in ~arc-scope.el~:

+ ~arc-knn-candidates~ (default 40) -- how many nearest neighbours
  retrieval wants, in or out of scope. For an unscoped query this is
  ~k~ directly; for a scoped one it is what ~arc-scope-vector-plan~
  scales ~k~ up to approximate, or the number of rows brute force pulls
  in scope order.
+ ~arc-scope-bruteforce-max~ (default 2000) -- the largest scope, in
  chunks, searched by brute force rather than a scaled-up KNN. Above
  it, ~arc-scope-vector-plan~ scales ~k~ by the ratio of corpus size to
  scope size; if that scaled ~k~ would exceed the 4096 ceiling, brute
  force runs regardless of cost, because there is no ~k~ that could
  work instead.

2000 was picked to keep brute force's worst case near 400 ms at
roughly 0.2 ms/row -- both defaults are plain numbers, not magic
constants, and are fair to argue with once your own corpus's size and
your own patience for a slow query are on the table.

Both actually take effect where the decision is made. ~arc-find-similar~
(what these two tune) runs inside a forked, ~emacs -Q~-equivalent child
process (~async-start~, via ~arc--async-do~), which never loads your
init file, so any ~defcustom~ read there sees only its compiled-in
default unless the parent explicitly captures the live value and hands
it across with ~async-inject-variables~. ~arc-knn-candidates~ and
~arc-scope-bruteforce-max~ are on that injection list, along with
~arc-limit~ and ~arc-reranker-limit~ (read via ~arc-get-limit~, which
picks the retrieval candidate limit) and ~arc-embedding-size~ (read when the
child opens its own database connection, which it always does, having
no cached one to inherit) -- so customizing any of these in your init
file does change retrieval in the real, asynchronous path, not just in
a synchronous call from ~M-:~. ~test/test-arc-async-injection.el~
guards this by walking the actual call graph the child runs and
failing if some future callee reads a new tunable that isn't on the
injection list.

** Measuring retrieval

~M-x arc-eval~ runs a set of questions through the real retrieval path and
reports recall at each cutoff in ~arc-eval-k~ (5 and 10 by default), into a
~*arc-eval*~ buffer that lists, per question, the rank each expected source
came back at -- or what came back instead.

It never calls the chat model. A run stays fast and deterministic that way, and
recall@k is a property of retrieval regardless: a model writing a fluent
paragraph out of the wrong five chunks is the failure this is built to catch,
not to paper over.

*** The question set lives outside this repo

~arc-eval-set-file~ defaults to ~~/docs/org/arc-eval.eld~. That is deliberate. A
set worth having names real targets -- file paths, org-roam ids, option names --
and this repository is public, so committing one publishes the shape of a
private corpus. A synthetic set ships at ~test/fixtures/eval-set-sample.eld~ to
keep the harness itself tested; it is a shape, not a measurement.

An entry is a plist. Every key in an ~:expect~ clause must match a retrieved
source for that clause to count, and ~:path-suffix~ matches the tail of a path so
a set survives being read on another machine:

#+begin_src elisp
((:question "how do I turn on syncthing in home-manager"
  :scope (:collections ("hm options"))
  :expect ((:kind "hm-option" :option-name "services.syncthing.enable")))

 (:question "which models does ollama pre-pull on this machine"
  :scope (:collections ("home"))
  :expect ((:kind "file" :path-suffix "ioshi/i-intelligence/ollama.nix"))))
#+end_src

Recognized ~:expect~ keys are ~:kind~, ~:option-name~, ~:org-id~, ~:info-node~,
~:path~ (exact) and ~:path-suffix~. An unrecognized key is a hard error rather
than a silent non-match -- a typo would otherwise read as a permanent retrieval
failure.

*** What it found

The harness was built to answer "is retrieval any good". The first thing it
found was that the question could not yet be asked: ~arc--retrieve-rows~ fetched
its rows with a bare ~WHERE d.id IN (...)~ and no ~ORDER BY~, so SQLite returned
them in rowid order and the entire hybrid ranking was discarded between the
search and the answer. The model had been receiving its context in essentially
arbitrary order, citations were listed by rowid rather than relevance, and
recall@k was measuring "is the expected source among the k lowest rowids".

Nothing caught that for three phases, because every suite asserted WHICH rows
came back and none asserted their ORDER. It surfaced here only as an
impossibility: asking for 20 candidates changed recall@5, which cannot happen
for a real ranking. ~test/test-arc-rank-order.el~ pins it now.

Three plausible improvements were then measured and *rejected*, which is most of
what a harness is for:

- *Stopword filtering* on the FTS query. BM25's IDF factor already discounts
  common terms, and doing it by hand cost recall: 0.45 at k=5 with filtering,
  0.55 without.
- *Lowering the RRF constant* from 60. The arithmetic is persuasive -- on a
  40-item pool, 1/(60+rank) nearly flattens rank away -- but swept at
  10/20/60/120 the spread is one to two expectations out of thirty-four, inside
  single-question noise.
- *Excluding oversized Info index nodes.* This corpus contains a
  594,549-character ~(elisp.info)Index~; across 330 retrieved results it was
  never returned once. BM25's length normalisation had it handled.

One change survived, plus one default. Weighting the vector arm at 2 against the
keyword arm's 1 (~arc-rrf-semantic-weight~) is better at every cutoff, and
~arc-limit~ moved from 5 to 10 because the target is so often just below the old
cutoff:

: as shipped   recall@3 0.33   recall@5 0.55   recall@10 0.76   25/33 questions
: now          recall@3 0.42   recall@5 0.58   recall@10 0.79   26/33 questions

The arms alone score 0.48/0.52/0.67 (vector) and 0.18/0.27/0.48 (BM25). The
keyword arm is weak at the top of the list and useful further down, which is
exactly the shape a reranker exists to fix -- arc has that code path, disabled,
and now has a way to find out whether it earns its service.

Thirty-three questions cannot resolve anything finer than this. Growing the set
is worth more than another sweep of the same one.

** Freshness and lifecycle

~M-x arc-freshness~ reports which collections have drifted from what is on
disk, and ~arc-tool-stats~ exposes freshness to external callers. ~arc-watch-mode~
keeps the mutable half current on its own.

~arc-tool-lifecycle~ and ~bin/arc lifecycle~ add a bounded, read-only report
for missing indexed files, stale or absent freshness, phantom sources, and
orphaned data rows. The report is an inspection aid for an operator or agent;
it never deletes, prunes, or reindexes. A synchronous ~arc-reindex-all~ remains
the explicit operation that can reconcile departed sources, while the
interactive asynchronous path intentionally avoids silent destructive cleanup.

*** Two mechanisms, because the corpus has two kinds of source

The obvious design -- hash every source, compare -- is wrong here, and
measurably so. Of 38,436 sources on a real corpus, 656 are genuinely mutable
(files and org nodes) and 37,780 are derived from immutable inputs: Info
manuals from a Nix store path, NixOS and Home-Manager options from a
~flake.lock~ revision. A derived source's content cannot change unless that
input changes, so hashing them individually is sixty times the work to learn
one bit per collection.

So mutable sources are compared by recorded content hash, and derived
collections carry a ~collections.provenance~ string -- a ~flake.lock~ hash, or the
resolved Info directory list -- compared as one value. An org node records its
FILE's hash rather than its own, deliberately, so a single staleness rule
covers both mutable kinds.

*** unknown is not stale, and neither is fresh

A collection indexed before provenance recording existed, or sources indexed
before hashing, have no evidence either way. Those report ~unknown~. Folding
them into ~stale~ would have made a real vault read as "417 sources just
changed", which is noise a reader learns to ignore -- and a freshness report
nobody reads is exactly what this replaces. Reporting ~fresh~ without evidence
would be the worse failure and is not done either.

*** arc-watch-mode

Re-indexes a saved file arc already knows, and sweeps for drift on a
300-second idle timer. The sweep is what catches changes ~after-save-hook~
never sees: a ~git pull~, a Syncthing update, an edit on another machine. It
examines ~arc-watch-sweep-batch~ sources per tick and resumes where it stopped,
because a sweep that rehashed every mutable source in one tick would be the
reason someone turned it off.

A saved file is re-indexed only if it lives under a *planned* collection's
directory AND ~arc-indexable-file-p~ agrees -- which shares its predicate with
the directory walk rather than reimplementing the ignore rules, so the watcher
cannot start indexing an SSH key that the walk correctly skips. "Planned"
matters because ~arc-collection-directory-alist~ deliberately configures
directories the plan does not build (~mail~): saving a file there must index
nothing at all. And because ~home~ is rooted at ~$HOME~ and is therefore a
prefix of every other collection's directory, the match is the *longest*
one -- otherwise a file under ~~/.config/emacs~ would land in ~home~ when saved
and in ~emacs~ when walked, and migrate between the two.

*** Derived collections are never reindexed automatically

A deliberate non-goal, against the spec's own wording. Rebuilding the option
collections means embedding some 30,000 chunks -- around 40 minutes of GPU --
and a NixOS rebuild changes ~flake.lock~ routinely. A ~nixos-rebuild switch~ must
not silently start a 40-minute background job. arc reports the staleness and
leaves ~arc-reindex-all~ to the operator, who knows whether now is a good time.

** Known limitations

*** Asynchronous reindex never removes departed sources

~M-x arc-reindex-all~ (the interactive, non-blocking path -- see its
docstring) does not prune. A source that has genuinely left the corpus
(deleted, gitignored, newly excluded) keeps whatever content it was
last indexed with and stays citable indefinitely under this path
alone. This is deliberate, not an oversight: a long-running
asynchronous walk only ever knows "what this run has reached so far",
never "everything this collection currently has", and three separate
attempts to prune from the former each turned into a real, reproduced
way to delete sources the run had simply not gotten to yet.

Only a *synchronous* reindex prunes -- run one occasionally to actually
remove departed sources:

#+begin_src elisp
(arc-reindex-all)                  ; every collection in `arc-index-plan'
(arc-reindex-all '("home"))        ; just one collection
#+end_src

*** Emptying a collection's only source leaves it indexed

The synchronous prune above refuses to prune anything when a
collection's walk comes back with zero sources, on purpose -- see
~arc--prune-collection~'s docstring -- because an empty result is
indistinguishable from a directory that is merely momentarily empty
(unmounted, a sync tool mid-catch-up), and deleting a whole collection
is never the right answer to that ambiguity. One consequence: if a
collection has exactly one source and that source is edited down to
zero chunks (an emptied or now-whitespace-only file, say), the walk
that reindexes it also comes back with zero kept ids, the same refusal
applies, and that now-empty source's *old* content stays indexed and
citable indefinitely -- reindexing never removes it, because from
here a genuinely-emptied sole source and a not-yet-ready directory
look identical. Adding an unrelated second source to the same
collection is enough to make the emptied one prunable again on the
next synchronous reindex, since the walk then yields a non-empty
kept-ids list to check it against.
